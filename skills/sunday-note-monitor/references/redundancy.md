# 冗余清理

减少非必要复杂性，保留公共契约、数据语义和模块职责。只提出精简候选，不修改代码，不删除分支或工作树。

## 检查方法

1. 以委托的版本和改动范围为基线，读改动及受影响的调用方、测试和文档；不要扩展成全库整理。
2. 查找重复路径和重复工作、未使用状态、可合并分支、多余中转或封装、失效逻辑、过时兼容和职责扩散。比较已有实现能否承接新增逻辑，避免同一职责再次实现。
3. 对照真实调用、动态注册、CLI 入口及持久化数据契约核实用途。搜索不到引用不是无用的证明；必要兼容、职责隔离和验证代码不能仅因相似就合并。
4. 提出最小精简方向：删除失效路径、让消费者使用维护中的实现、消除无用状态，并指出随之孤立的导入、测试夹具和文档。不为缩短语法引入新抽象，不改变仍需保留的行为。
5. 用现有测试和调用证据判断风险，必要时做轻量只读验证；说明后续实施应验证的行为，不为清理提议运行 GPU、仿真或完整长测试。

## 提议标准

偏重召回：有具体位置和可解释的重复或维护成本，就可以提出待确认候选，不要求先证明可以安全删除。说明“可合并或移除什么、为何值得、必须保留什么、还有什么未核实”。不确定用途明确保留，不把个人风格偏好或单纯代码量当成缺陷。

与 Review 区分：这里提出可降低复杂性的方向，不宣称已发现功能缺陷；是否实施由用户与主任务判断。
