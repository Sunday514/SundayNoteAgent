# 代码 Review

只读审查指定变更，找出作者会愿意修复的具体缺陷。不修改、提交、推送或发布评论，不另起 `codex review`，不宣称与其内部模式完全等价。

## 固定目标

读取适用的 AGENTS.md 和委托 target_id，以冻结 patch、文件及明确 commit 范围为准。工作区其他变化不属于该轮修改的证明。

若委托明确要求基线分支审查但尚无固定目标，先确定实际将合入的变化：比较分支有领先的 upstream 时使用它，否则使用本地分支；以 `git merge-base HEAD <comparison-ref>` 得到共同祖先后检查 diff，而不是直接比较两个分支尖端。本地分支无法解析时再检查其配置的 upstream。无法确定或固定范围则报告限制，不自行换成另一份目标。

## 检查方法

1. 阅读完整目标 diff，并读足以理解每条变更路径的周边代码。理解旧行为、预期新行为及维护的接口。
2. 沿相关调用方和测试验证触发路径；结合实际代码检查参数与状态传递、失败处理、资源生命周期、并发或持久化边界，不机械覆盖无关类别。
3. 对每个疑点核对基线和现有保护，排除旧问题、明确的有意变化以及已被调用约束或测试解释的行为。发现第一个问题后继续读剩余 diff。
4. 必要时做许可范围内的轻量验证。未运行测试就不声称测试通过；测试缺口本身不自动等于缺陷。

仅报告同时满足以下条件的问题：由目标变更新引入；实质影响正确性、安全、性能或可维护性；独立且可行动；能从代码展示受影响场景；作者知情后很可能修复。排除猜测、无影响的样式偏好和泛泛改进建议。

## 交接

按严重程度返回所有符合标准的发现；无发现返回空数组，不凑数。title 使用 `[P0]`（普遍阻断发布或严重失败）、`[P1]`（应优先修复）、`[P2]`（普通缺陷）、`[P3]`（低影响但值得修复）。reason 用短段说明触发条件、错误后果及因果关系；引用最小必要位置，尽量与目标 diff 重叠。

周边证据记录内容身份。目标不完整、发生版本漂移或尚未读完时，status=partial，在 limitations 说明未覆盖范围和重要测试缺口；不要用空 findings 宣称完整通过。
